# Mandatory atomic task claim protocol

**Before any task-specific audit, implementation, tests, or code edits**, agents must **select and claim their own task** on GitHub. Reading the queue and checking task eligibility is permitted before claiming. The agent should initiate the claim workflow itself, without a separate human dispatch approval. See [self-assignment instructions](AGENT_SELF_ASSIGNMENT.md).

1. Fetch the live queue, issues, open PRs, and remote refs. A task is unavailable if it has an active claim, a task PR, or is completed/blocked. Do not rely on a stale local checkout.
2. For task ID `<TASK_ID>`, **the agent dispatches** the trusted GitHub Actions `claim-request.yml` workflow itself on the designated default branch, supplying task, agent label, work branch and scope. The workflow creates the **fixed, exclusive** remote `claims/<TASK_ID>` ref using GitHub's create-only API; it fails if that ref already exists. Never force, reset, upsert or create agent-specific claim-ref alternatives. The shared name is the mutex.
3. A successful **workflow dispatch is not itself a claim**. Only after the workflow completes successfully and the exact claim ref and matching published ownership record are independently verified may the agent begin. If the workflow reports a definite conflict, choose the next eligible task. If the dispatch or create result is ambiguous, **stop and reconcile** before doing anything else. Do not retry blindly or assume the task belongs to this agent.
4. The trusted workflow **automatically publishes** the claim ownership notice: in SRM 1D to the designated issue #12 ledger; in openMotor to a commit comment on the verified base SHA. It records task, self-declared agent label, authenticated `github.actor`, workflow run, claimed ref, work branch, base SHA and scope. If publication fails, the claim remains locked and the agent **stops for reconciliation**. Do not begin work based on claim-ref existence alone.
5. Recheck the claim ref, **matching owner ledger entry**, and latest task/PR status **before starting work**. Create the normal implementation branch recorded in the ledger after the claim, not as the claim itself. Never work on the lock branch.
6. On completion, link the implementation PR and record `READY FOR REVIEW`. On abandonment, report `ABANDONED` and reason; **do not claim release unless an authorized coordinator has actually verified and released it**. **Do not delete the lock branch automatically**. A claim remains unavailable until separately approved reconciliation. A stale timestamp alone does not permit stealing a task. Agents must stop after PR submission until the supervised pilot owner approves a new work cycle.
7. Agents must never claim a task in the other repository on behalf of their current repository. Cross-repository dependencies require separate claims.

**Concurrency guarantee and limitation:** An exclusive remote ref creation can serialize competing agents even if they start seconds apart, provided the GitHub API truly uses create-only semantics. Comments, labels, and issue assignment are visible status signals, **not atomic locks**. The protocol prevents simultaneous task ownership; it does not by itself solve abandoned locks, offline work, or permissions failures. Coordinate recovery explicitly.
