# Mandatory atomic task claim protocol

**Before any task-specific audit, implementation, tests, or code edits**, claim the task on GitHub. Reading the queue and checking whether a task is eligible is permitted before claiming.

1. Fetch the live queue, issues, open PRs, and remote refs. A task is unavailable if it has an active claim, a task PR, or is completed/blocked. Do not rely on a stale local checkout.
2. For task ID `<TASK_ID>`, attempt to create the **fixed, exclusive** remote branch `claims/<TASK_ID>` from the current verified task base commit. Use GitHub's create-ref/create-branch operation that **fails if the ref already exists**. Never use force, reset, or an upsert operation. Do not add an agent name or timestamp to this branch name: the shared name is the mutex.
3. **Only the agent whose create operation succeeds owns the claim.** If GitHub says the branch already exists, or the result is ambiguous, treat the task as unavailable. Re-fetch the ref and issue; do not assume a retry succeeded. Select another task. If the connector cannot guarantee create-only semantics, do not treat it as an atomic lock; stop and request a suitable mechanism.
4. Immediately publish the claim: for an issue, post `CLAIMED by <agent/run identifier> at <UTC timestamp>; lock: claims/<TASK_ID>; work branch: <branch>; base: <SHA>; planned scope: <slice>` as an issue comment and, where supported, apply an `in-progress` label/assignment. For Markdown-only tasks, add the same notice to the associated draft PR discussion or designated task-status record. If publishing fails, stop and report the claim for reconciliation; do not silently work.
5. Recheck the claim ref and latest task/PR status **before starting work**. Create the normal task-specific work branch after the claim, not as the claim itself. Never work on the lock branch.
6. On completion, link the implementation PR and record `READY FOR REVIEW` or `COMPLETED`. On abandonment, record `RELEASED` with reason. **Do not delete the lock branch automatically**: GitHub deletion requires explicit authorization or a separately approved cleanup policy. An existing claim remains unavailable until an authorized coordinator verifies and releases it. A stale timestamp alone does not permit stealing a task.
7. Agents must never claim a task in the other repository on behalf of their current repository. Cross-repository dependencies require separate claims.

**Concurrency guarantee and limitation:** An exclusive remote ref creation can serialize competing agents even if they start seconds apart, provided the GitHub API truly uses create-only semantics. Comments, labels, and issue assignment are visible status signals, **not atomic locks**. The protocol prevents simultaneous task ownership; it does not by itself solve abandoned locks, offline work, or permissions failures. Coordinate recovery explicitly.
